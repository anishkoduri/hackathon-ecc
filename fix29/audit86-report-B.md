## New findings

### 86-B1 — MINOR (verifier) — 9b counts matching lines, not name occurrences, so a second model name on an existing GLOBAL-ROUTING line is invisible to it

**Evidence.**

- `verify29.py` 9b (name half): `_dsq` is the list of `grep -rn -E "DeepSeek|Qwen"` output lines outside the icon-data allow-list, and the check asserts `len(_dsq) == 2 and all("GLOBAL-ROUTING" in ln for ln in _dsq)`. That is a line count, not an occurrence count.
- In the #85-B3 X1 scratch test (see above), appending `Send coding work to Qwen now.` to both GLOBAL-ROUTING lines left 9b PASSING: each block line already contains one Qwen (the forward reference), so the grep still returns exactly the same 2 lines. Total: 290/292 — the two failures are the golden-pin checks only.
- The live tree is currently correct: each block carries exactly one DeepSeek and one Qwen (the fix-#30 forward reference), confirmed by direct count. And the golden pin now closes the exploit class the X1 mutation demonstrated — any in-block addition fails two checks. So 9b's weakness is defense-in-depth only, not a live hole.

**Why it matters.** 9b's stated property is "DeepSeek/Qwen names occur only in the GLOBAL-ROUTING block" — as written it enforces "on a GLOBAL-ROUTING line", and it cannot distinguish one name per line from two. If the golden pin were ever weakened or the golden file itself edited to match a smuggled block, 9b would be the last guard and it would not fire. Same class as 85-B3, one layer down.

**Fix.** Assert occurrence counts as well as the line count: e.g. total `DeepSeek` occurrences outside the allow-list == 2 and total `Qwen` occurrences == 2 (one of each per block), or per-line `ln.count("DeepSeek") == 1 and ln.count("Qwen") == 1` for each of the two `_dsq` lines. Verifier-only change; no tree change needed.

### 86-B2 — MINOR (verifier) — 7d(c) asserts only the out-of-scope half of feature-expansion format item 2; the files-in-scope half is unasserted

**Evidence.**

- `verify29.py` 7d(c) item-2 check asserts only `"and the files explicitly OUT of scope (named; `none` if genuinely none)" in _fe`. The item-2 line in the tree (`skills/feature-expansion/SKILL.md:145`) is "…and which files it touches — and the files explicitly OUT of scope (named; `none` if genuinely none)…". The "which files it touches" (files-in-scope) half has no assertion anywhere: the factory paragraph's sentence ("the brief format below already carries the goal, the files in scope and explicitly out of scope (item 2)…") asserts the paragraph's claim, not the format item's content, and it survives the mutation untouched.
- Demonstrated false-pass (my own test, beyond the #85-B cases): in a scratch copy, deleting `and which files it touches — ` from item 2 leaves verify29 at **292/292**. The format item no longer names the files in scope, while the paragraph above it still claims it does.
- The live tree is currently correct: item 2 carries both halves. So this is latent only — the same class 84-B1 closed for items 1 and 3, with item 2's in-scope half never covered.

**Why it matters.** DIRECTOR-BRIEF's files-in-scope slot is one of the seven required fields, and item 2 is the only place the feature-expansion format carries it (item 1 is goal/fit, item 3 is constraints). A later edit that drops the in-scope clause while keeping the out-of-scope clause would pass verify29 while shipping a brief format that no longer tells the drone which files it touches.

**Fix.** Assert the in-scope half of item 2 the same way item 3 is asserted — e.g. `"which files it touches" in _fe` or the full item-2 line. Verifier-only change; no tree change needed.
