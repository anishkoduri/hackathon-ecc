## New findings

### 87-B1 — BLOCKING (tree) — react-build pointer claims orchestrator verification, but the command has no orchestrator verify step and no correction-brief path; verification is the resolver's self-check alone

**Evidence.**

- `commands/react-build.md:9–10` (the 86-A1 pointer): "the react-build-resolver runs as a single-task factory drone with a director brief (goal, files in/out of scope, constraints, acceptance criteria, verification steps, what to return), no-guessing, and orchestrator verification against the brief's acceptance criteria (the re-run build is evidence, not the verdict)."
- The command's procedure (steps 1–5) contains no orchestrator verify step. Step 4 is the resolver's own loop ("Fix Incrementally: One error at a time, re-running build after each change"); step 5 is "Report Summary" — the resolver's own summary. There is no step in which the commanding agent checks the resolver's output against the brief's acceptance criteria before presenting it, and no re-dispatch path on failure.
- `"correction brief"` occurs **0×** in `commands/react-build.md`. Every other drone-output consumption site names the correction-brief path (orchestrate ladder :252, feature-expansion fix loop :158, orch-pipeline Phase 5 Review :74, gan-build ORCHESTRATOR-CHECK :61 + planner-spec 3a :30, redesign :68). React-build is the only one without it.
- The only verification in the executed flow is the resolver's own: `agents/ecc-react-build-resolver.md:82` ("5. Re-run build → verify fix") and its own Final verdict line (:207: `Build Status: SUCCESS | Errors Fixed: N | Files Modified: <list>`). The resolver's "Key Principles" (:187–190: surgical fixes only, never disable type-checking, never add `// @ts-ignore` without explanation) are the resolver's own rules, not a check anyone performs on its output.
- The pointer's own sentence is self-defeating as written: it demotes the re-run build to "evidence, not the verdict" — implying a verdict step exists — while no verdict step exists anywhere in the command or the agent file. A resolver output that passes the build but violates the brief's constraints (a `// @ts-ignore` with a thin explanation, a fix beyond minimal scope, a suppressed symptom) is presented via the summary with no orchestrator check and no correction route.

**Why it matters.** This is the exact 81-B2 structural defect, which was blocking then: the routing text states the verify step, but the executed wiring terminates on the drone's own signal. The build passing is stronger evidence than the GAN rubric score was, so the practical exposure is narrower — the gap is constraint violations that still leave the build green, not a wholly unverified pass — but by the fix's own standard the output is merged unverified: the pointer names a verdict that no procedure performs. The 86-A1 fix as specified ("a one-line factory pointer") was implemented exactly as specified; the gap is that the pointer is the whole fix, where the gan-build precedent it followed later needed the loop wiring (81-B2) to make the same claim true.

**Fix.** Add an explicit orchestrator verify step to `commands/react-build.md` after the resolver returns (mirroring `gan-build.md`'s ORCHESTRATOR-CHECK): the commanding agent checks the resolver's output against the brief's acceptance criteria — build green AND minimal scope AND no unexplained suppressions — and on a failed criterion re-dispatches the resolver with a correction brief naming the failed criterion and the required correction, distinct from the original brief (capped like the other fix loops, e.g. the resolver's own 3-attempt stop condition). Add a verify29 assertion for the new step (full step text, not a prefix) and extend the 86-A1 pointer check from its current prefix-only form (see the verifier-honesty table, 10i) to the full pointer including the verification sentence. Tree + verifier change.
