# Grill Me

**MODEL check (fix #33, MODELSEL_F33):** before anything else, state the model the orchestrator is running on and record it in the run ledger (`MODEL: <name>` — the actual selected model). If the selected model is Auto, or the model cannot be determined to be a specific model, tell the user to pick a specific model before proceeding; do not silently orchestrate on an unknown fallback.

Before anything is scoped, built, or expanded, make sure the idea is actually decided. This skill asks the user one question at a time about their hackathon project until every material branch has an explicit recorded decision. The decision record it produces is what the rest of the plugin works from — scope, build, and expansion all follow it, so the product ends up going the direction the user wants instead of the direction the agent guessed.

## When to Use

- The user sends the first hackathon project prompt (an idea plus requirements). Run this skill FIRST, before `hackathon-scope`, before any building, and before any expansion skill. This is the default, not an option.
- The user says "grill me", "ask me questions", or "stress-test this idea".
- The user wants to be questioned about a plan or design before it is built.

## When NOT to Use

- The user says "skip the grilling" or "just build it" — go straight to `hackathon-scope`.
- The idea is already fully decided (the user gave a complete spec with every decision made). Before taking this shortcut, check the hours-left (question 2) and named-API (question 3) status are in the record: if either is missing, ask it — or record the default ("8h assumed" for hours-left, "none named" for the API) — never silently skip either. Skim for open branches; if there are none, write `docs/decision-record.md` first (work in the project root — the folder opened in Cursor — and create `docs/` under it if it does not exist; see step 5), then say so and move on.
- Bug fixes or small changes to an existing project — that is not a first prompt.

## Workflow

1. Extract the current objective, constraints, assumptions, and already-made decisions from the user's first prompt and anything they have already said. Investigate any answer discoverable from the supplied material instead of asking the user.
2. Maintain a running decision record with: decision, chosen option, rationale, dependencies, and consequences. Update it after every answer; do not reopen a recorded decision unless new evidence conflicts with it. **Adapt to how much the user specified (fix #25 §4(f), ADAPT_F25).** Before the first question, assess specified-ness: count how many material decisions the prompt already makes (product, users, features, constraints, design direction, stack, named API). A big, complete prompt gets EXECUTION posture: verify the decisions are complete (the mandatory Q2/Q3 check below), write the record, and move on — do not re-ask what the user already decided. A vague one-liner gets REASONING posture: the questions do the reasoning work — infer the domain and its conventions, the user, the constraints, the demo, and the wow moment — propose options with reasons, and record every inference explicitly as INFERRED (see the record format in step 5), never as if the user stated it. Between the poles, the posture follows the prompt: ask only what is undecided, execute what is decided. Every record entry carries a Source tag — USER-STATED, INFERRED (with the reasoning one-liner), or ASSUMED (a default, marked assumed, not user-stated). Ask the mandatory first questions in this fixed order before any lower-leverage branch (step 4): (1) what the product is and who it is for; (2) how many hours are left — mandatory, ask it as question 2, right after "what is the product", even if the user has not mentioned time; (3) the named API / integration — which API or integration the demo must use, whether it exists, and what it does (if the prompt names one; if none is named, record "none named" and move on). Record the time budget in the record too: store the hours-left number in the decision record — `hackathon-scope` copies it into `docs/scope.md`. If the user stops answering before giving the hours-left number, do not block: use the default — the remaining time until the demo deadline if known, else 8 hours — and record it in the decision record as an assumption, clearly marked as assumed, not user-stated. Write the record to `docs/decision-record.md` INCREMENTALLY — after EVERY answer, update the file (create `docs/` under the project root first if needed), so a walk-away never loses the record; the file is the durable record, the reply alone is not enough.
3. Ask exactly one question at a time. Format the turn as `### Decision <N> — <topic>`, then `Recommended`, `Why`, `Tradeoff`, and `Question`. Ask the mandatory first questions in the fixed order in step 2 (product, then hours-left, then the named API / integration), then choose the highest-leverage unresolved branch whose answer constrains the most downstream decisions. After each answer, acknowledge `Recorded: <choice> — <consequence>` before the next question, and update `docs/decision-record.md` with that answer before asking the next question (step 2's incremental write). Show settled and currently open counts when useful; never show a percentage because the decision tree can grow. **"Stops answering" means: no reply to the next question — the user walks away. A chat agent cannot self-wake, so silence alone starts nothing: if the user walks away, the build resumes on their next message — the record is already saved incrementally (step 2), so nothing is lost.** Ask at most ~6 questions, highest-leverage first (the mandatory product / hours-left / named-API questions in step 2 come first). Expect about two minutes of questions as a sense of scale for the user's time — that is a loose guide only, never a stop condition the agent measures: there is no wall-clock timer in chat and no clock to stop on; the cap that binds is ~6 questions. Stop asking when the user stops answering or when the ~6-question cap is reached: do not chase the user. **Proceed-on-next-message:** if the user replies with anything other than an answer (for example "go", "build it", "just build it"), or if the user's next message comes after a silence, proceed on the partial record (step 5) immediately — never wait for an answer.
4. Work through the branches below, but only where they are material to this project. The mandatory first questions (step 2) come before these lower-leverage branches: product first, hours-left second, named API / integration third. Skip any branch that does not matter for a hackathon demo:
   - What the product is and who it is for (already asked as question 1 — do not re-ask)
   - The core demo: what the judge sees in the 2–4 minute demo window, and what the wow moment is
   - Must-have features vs. nice-to-have features (what gets cut if time runs short)
   - Data and state: what data the product needs, where it comes from, what is fake or seeded for the demo
   - Stack and platform: what it is built with, and whether it is web, mobile, or both
     **Platform constraint — never silently convert (fix #25 §4(c), PLATFORM_F25).** This plugin builds responsive web apps; it does not build native iOS (Swift/SwiftUI), native Android, or desktop apps. If the user names a platform the plugin does not build, do NOT convert it silently to web: state the constraint, name the options (a web build now, or a native build outside this plugin), and ask the user to choose BEFORE scoping — record the choice in the decision record. A build that started as a native-app request and proceeded as web with no recorded choice is an incomplete build.
   - Integrations and tracks: which APIs, tools, or sponsor tracks it must use (see `integration` and `track-picker`) — the named API / integration identity and existence were already asked as question 3; here only follow up on tracks or additional integrations, do not re-ask question 3
   - Failure modes: what happens if the demo path breaks, the API is down, or the wifi drops
   - Time: how many hours are left, and what the stopping criteria are (when it is done enough to demo) — hours-left was already asked as question 2; do not re-ask it, only ask the stopping criteria if still open
   - Success: what "good" looks like at demo time
   Do not ask about migration, rollout, operations, or ownership unless the user brings them up — those are not hackathon decisions.
5. When no material open branches remain — **or the user has stopped answering, or the ~6-question cap is reached** — work in the project root (the folder opened in Cursor — the project directory IS the project root; no separate directory is created; create `docs/` under it if it does not exist), then finalise the incrementally-written decision record in `docs/decision-record.md` in the project — write the header line `grill-me: RAN` (fix #27, GRILLHDR_F27) at the top of the record: the header states whether grill-me ran, was skipped, or was missed (`grill-me: RAN | SKIPPED (user said "<phrase>") | MISSED (no trigger)`), so a later reader can tell a grilled record from a stub; grill-me writes RAN here, hackathon-scope writes SKIPPED/MISSED on the stub path — the record has been written after every answer since step 2, so this step completes it rather than writing it for the first time — a decision/choice/rationale/consequence table, with every entry in the mandatory three-part reasoning format (fix #25 §4(f), REASON_F25): **INFERRED** (what was inferred from the prompt or the domain, and the reasoning — or `none — everything user-stated`), **CHOSEN** (what was decided, with its rationale), **REJECTED** (what was considered and rejected, with the reason for each) — plus a Source tag per entry (USER-STATED / INFERRED / ASSUMED), the hours-left number (or the recorded hours-left assumption from step 2 if the user stopped answering before giving it), `### Risks`, accepted unknowns (each with an owner and a resolution point), rejected alternatives that matter, and `### Completion criteria`, plus one `Design direction:` line — the product's design direction (theme/axes/mood, named from the brief's mood/domain). If the user said nothing about look/feel, record the stated default as an assumption (marked assumed, not user-stated), derived from the brief's mood/domain — never leave the line blank: `hackathon-scope` and orchestrate's slice briefs build on it, and every UI slice restates it in `docs/design-tokens.md` before building UI — and only then return the same record in your reply under `### Decision record`, followed by `### Risks`, the accepted unknowns, the rejected alternatives, and `### Completion criteria`. Creating `docs/` under the project root before this write is not scaffolding — scaffolding happens later, in `orch-build-mvp` Phase 3. The file is the durable record every later skill reads; the reply alone is not enough. Do not end with another question. Unanswered material branches become accepted unknowns (owner: the builder, resolution point: during the build, per hackathon-mode §7's assumption rule) — they are not blockers.
**Design-decision pointer:** F2/F3/F4/F5/F6/D19/B1/X1 as relevant — design-package rule — Taste step 4a / orchestrate.

Every accepted unknown carries an owner and a resolution point (who resolves it, and when — during scoping, during the build, or at demo rehearsal). Per hackathon-mode §7's assumption rule, an accepted unknown becomes a stated assumption during the build: the builder resolves it by the safe/reversible default, states the assumption, and logs it in the stage ledger and the final report — it is never silently guessed or left unresolved.

Completion requires every material branch to have a recorded decision or an explicitly accepted unknown with an owner and resolution point. A partial record is complete when the user stops answering, replies with anything other than an answer (proceed-on-next-message, step 3), or the ~6-question cap is reached — the unanswered branches are accepted unknowns, not blockers, and the build proceeds on the partial record.

## After Grilling

The decision record is the input to everything that follows. Finalise the incrementally-written record in `docs/decision-record.md` before returning (step 5 above), then hand it to `hackathon-scope` (which turns it into the must-have/cut lists and the demo storyboard in `docs/scope.md`), and keep it available for `feature-expansion` (which expands the product in the direction the record points, not a direction it invents) and `integration` (which reads `docs/decision-record.md` at the start and wires the integrations the record names). `orchestrate` picks the record up next: grill-me output feeds orchestrate's resume guards (orchestrate steps 0–2 verify the record, scope, and expansion briefs exist and do not re-run them) — orchestrate does not re-grill. If a later skill proposes something that contradicts a recorded decision, the recorded decision wins — note the conflict instead of overriding it.
