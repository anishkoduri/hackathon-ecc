# orch-build-mvp

Actor · action · target: **orch · build · mvp**. Thin wrapper over the shared
engine in [`orch-pipeline`](../orch-pipeline/SKILL.md).

**One build engine per run:** this skill is the STANDALONE pipeline — it runs only when the user invokes `/orch-build-mvp` directly. Orchestrate IS the first-build engine; orchestrate never invokes this skill in the same run, and this skill never runs in a first build orchestrate is driving. One engine per run, never both. The GAN harness (orch-build-mvp step 4 below) is the implementer loop WITHIN this standalone pipeline (generator → evaluator per slice), not a separate build engine.

## When to Use

- The user explicitly invoked `/orch-build-mvp` (standalone run) and wants a working vertical slice bootstrapped from the record/scope — `docs/decision-record.md` + `docs/scope.md` by default.
- A doc path in `$ARGUMENTS` (e.g. `civicpulse/docs/SDD-v0.6.md`) is only the standalone fallback when neither record file exists — the record/scope is the default, never the doc path.

## Operation settings

- **Default size floor:** large — this is the full pipeline including Scaffold.
- **Phase mask:** 0 (read the record/scope by default; the spec doc in `$ARGUMENTS` is only the standalone fallback) → 1 → 2 (heavy) → 3 (scaffold) → 4 → 5 → 6. The mask lists the phases that run across the whole skill — NOT the phases step 1 runs: orch-build-mvp step 1 runs orch-pipeline Phases 0–2 only (see the phase mapping in step 1).
- **First move (phase 0 → 2):** read `docs/decision-record.md` + `docs/scope.md` by default — the grill-me decision record and the scope output — and extract scope, locked decisions,
  and the feature list; order it into **thin vertical slices** (one end-to-end
  path first, not all-models-then-all-views). Orch-pipeline Phase 3 (orch-build-mvp step 3) stands up that first slice. If neither record file exists (standalone run, no grill-me), fall back to the doc path in `$ARGUMENTS` or the raw prompt with a stated assumption — never ask the user for a path during a first build.

## How It Works

**Precondition — before the first build auto-approves anything:** check that `docs/decision-record.md` exists (grill-me recorded the decisions) OR the user explicitly chose the skip path ("skip the grilling" / "just build it"). If neither holds, do not auto-approve with zero recorded decisions and no check: proceed on the raw prompt with a stated assumption — do NOT re-run `grill-me` (see hackathon-mode §7).

**Narration-key prompt — once, at the start of the standalone run, never blocking.** At the start of the run (step 1), if narration will need a key and none is set (no `ELEVENLABS_API_KEY` in the environment, no MiniMax credentials), issue the single `pitch-deck-video` narration-key prompt once (ElevenLabs free tier — 10,000 characters a month, no credit card — with the free-tier facts), then continue the build immediately without waiting: the prompt never blocks, the key is an env var only and is never written to any file, and if it never arrives the video renders music-only/silent with a note in the final report. This is the ONE sanctioned user prompt during the standalone run besides grill-me itself (hackathon-mode §7 carve-out) — never a wait point, never an approval gate. Do NOT re-prompt at step 8 `/demo` time: the single early prompt covers the run, and `/demo` uses the key if present, else falls back to music-only/silent. **Key handoff to step 8:** if the user replies with a key mid-run, hold it in working context ONLY and pass it to the step-8 `/demo` via the dispatch: the step-8 dispatch carries an explicit env instruction naming `ELEVENLABS_API_KEY` with the value held in working context, and the `/demo` executor runs the `tts` step with that variable set in its process environment — the key travels in the dispatch (working context), never in a file; `tts.mjs` reads it only from the environment. If the key arrives after step 8 already rendered but before the step-9 final report, re-run the video script step (`npm run script` in the video project — tts + render) with the key set, so the delivered video is the narrated cut; if it arrives after the report, note the re-run command in the report with the key redacted (`ELEVENLABS_API_KEY=$KEY npm run script` in the video project dir — the user supplies their own key).

1. Run orch-pipeline Phases 0–2 ONLY (Intake/Research/Plan) with the settings above — read the record/scope, extract scope, locked decisions, and the feature list, order it into thin vertical slices, ending at Gate 1 (slice plan). This step does NOT run the full orch-pipeline engine (phase mask 0→6): the later numbered steps ARE orch-pipeline Phases 3–6, each running once — orch-build-mvp step 3 is Phase 3 (Scaffold), step 4 is Phase 4 (Implement, GAN loop), step 6 is Phase 5 (Review), step 7 is Phase 6 (Commit). Nothing is run twice and nothing is redone.
2. **Expand automatically — split, not whole (standalone run).** Right after scoping and before building the slices, run `feature-expansion` Phases 0–3 (ground, brainstorm, consolidate, planner pass): it brainstorms features and tools in line with the grill-me decision record, the planner approves, tweaks, or rejects each one, producing the approved list — with no user approval gate. **No double-run:** expansion Phases 0–3 run ONCE per run — here, in a standalone `orch-build-mvp` run; in an orchestrate-driven first build, orchestrate runs them instead. Expansion Phases 4–6 run INSIDE this build, not here: expansion Phase 4 implementers build the approved expansions alongside the MVP slices (the orch-build-mvp step 4 GAN loop drives each slice, expansions included), expansion Phase 5 verification runs in orch-build-mvp step 6 after the MVP is built, and expansion Phase 6 feeds the final report (orch-build-mvp step 9). The skill is never invoked whole at this step. The user removes anything unwanted with one prompt afterward.
3. **Scaffold — orch-pipeline Phase 3.** Stand up the first end-to-end slice via `app-scaffold` (the first thin vertical slice from orch-build-mvp step 1). The scaffold owns the final file layout: if a later implementer must move a file from the intended layout, the implementer records the move in its result and the orchestrator reconciles it in orch-build-mvp step 5 (Reconcile).
4. **Implement — orch-pipeline Phase 4: reuse the existing GAN harness** instead of hand-rolling an iterate loop (this step IS orch-pipeline Phase 4, not a rerun of it):
   - Translate the record/scope (or the fallback spec doc, if that was the input) — plus the planner-approved expansion list from `docs/expansion.md` (or the ledger's expansion section) — into `gan-harness/spec.md` + `gan-harness/eval-rubric.md`
     (this stands in for what `gan-planner` would generate — you already have the spec). Have the first UI slice in the GAN loop write `docs/design-tokens.md` from its design system (per orchestrate's no-landing fallback) so later slices brief from real tokens.
   - Drive the build with `/gan-build "<one-line brief>" --skip-planner`
     (defaults: `--max-iterations 15`, `--pass-threshold 7.0`,
     `--eval-mode playwright`; use `--eval-mode code-only` for non-UI slices).
   - That command runs the `gan-generator` → `gan-evaluator` loop and writes
     `gan-harness/feedback/feedback-NNN.md` until the score passes or plateaus.
   - **TDD inside the GAN loop (this step IS orch-pipeline Phase 4, which is TDD):** the generator writes tests FIRST per `tdd-guide` (red → green → refactor) for each slice's new/changed behaviour before implementing it, and the evaluator RUNS those tests as part of its check — a slice whose tests fail cannot score a pass. The loop's live-app evaluation does not replace written tests. The standalone flow ends with tests on disk for the new/changed behaviour, per hackathon-mode §4 ("Plan first, write tests first") and the pipeline Verification checklist ("new / changed behavior has tests; coverage ≥ 80%") — if coverage cannot reach 80% in the time left, the gap is recorded in the final report with the uncovered areas, never silently dropped.
   - Expansion Phase 4 runs here: the GAN loop drives each slice, expansions included, per the feature-expansion Phase 4 brief format (Tool/API cell + UI rule + capped 2-round fix loop + per-feature `code-reviewer` pass). **Belief in the brief:** implementers trust the brief and build it — they do not second-guess the plan, hedge, or wait for reassurance; they commit to the approach and make it work; if a detail is ambiguous, they pick the reasonable option and note it, they don't stall.
5. **Reconcile after each wave — this step owns collision reconciliation.** After each implementer wave, read every implementer's result (status, changed files, verification evidence, blockers) — the GAN loop's results are `gan-harness/build-report.md` and `gan-harness/feedback/feedback-*.md`; read those files, not just the return texts; confirm the reported files exist, stayed in scope, and carry verification evidence. If two implementers in the same wave touched the same files, decide the merge order — the first-listed implementer's files win on conflict unless the planner marked a dependency (then the dependency's files win) — record the decision in `.hackathon/run-ledger.md`, and dependents proceed on the merged result. If the scaffold's first slice and an expansion feature touched the same files, the same rule applies (scaffold first unless the planner marked the expansion as the dependency). If an implementer moved a file from the planner's intended layout, record the actual layout in the ledger and use it in later briefs. This step owns reconciliation — this skill runs standalone only, so there is no orchestrate-driven case in which orchestrate would own it instead.
6. **Verify — orch-pipeline Phase 5 (Review) + expansion Phase 5.** `code-reviewer` (+ `security-reviewer` on any security-trigger slice) reviews each slice; then run the whole-build verification: expansion Phase 5 checks BY NAME — `browser-qa` / `click-path-audit` / `verification-before-completion` per feature, after the MVP is built. Review findings are fixed inside the capped 2-round fix loop; past that, the item is recorded blocked with evidence and work moves on.

**Adversarial audit (a distinct named step, inside step 6, after the `code-reviewer` pass):** `code-reviewer` (+ `security-reviewer` on any security-trigger slice) audits the built code as a skeptical staff engineer — try to break it, falsify the claimed behaviour. Every finding carries a severity (blocker / major / minor) and is marked **confirmed** (reproduced against the running code) or **suspected** (reasoned but not reproduced) — a suspected finding is never presented as a confirmed defect. Fix blockers and majors inside the capped 2-round fix loop; minors go in the final report.

6b. **Final polish — after verification and before the step-7 commit.** Run `polish-pass` on the built UI (same role as orchestrate step 5b: it implements the subset that materially increases quality without destabilizing the build, at most one fix round per item) and carry its 10 highest-impact remaining improvements into the step-9 final report.

7. **Commit — orch-pipeline Phase 6.** Commit the scaffold and each slice as separate `feat:` commits → **Gate 2** (pre-commit; auto-approves during a hackathon first build after grill-me, or a one-prompt removal of a first-build feature — proceed without waiting; see hackathon-mode §7). Gate 1 (slice plan) was already passed in orch-build-mvp step 1 — it is not re-stopped here.
8. **Deploy via `deploy-fast`, then film via `/demo` (`pitch-deck-video`) — LOCAL only.** Deploy the working MVP — record the production URL and the deploy path used in `.hackathon/run-ledger.md` (Vercel CLI link, git-linked push, Railway, static-only, or blocked with the failing command and error) — then film the LOCAL app from the project dir (`APP_DIR` to the app dir) — `/demo` never films the deployed URL, so do NOT set `shots.json` `app.url` to it. The demo video is a required deliverable; its file is `<app-name>-video/out/demo.mp4`. If deploy was static-only or blocked, the final report notes that — never hard-abort the run for lack of a deployed URL. After filming, invoke `readme-writer` to write/update the README from the built app, before the final report in step 9 (the README is what `devpost-autofiller` later drafts the Devpost submission from).
9. **Deliver the final report — this is the done signal.** Before writing the report, run the six deferred end-of-project checks by name (`verification-loop`, `production-audit`, `delivery-gate`, `codehealth-mcp`, `santa-method`, `security-scan`) and record each result in the report (check name, pass/fail, findings count). (Per the hackathon-mode §3 carve-out, this run is the very end of the project, not 'during the first build' for the deferral rule; it runs once, after deploy/demo/commit/README, and never gates a feature.) Write it to `docs/final-report.md` in the project AND deliver it as the reply. State what was built, every assumption made, anything blocked or skipped, and anything the user may want to remove, with the files for each removable item (feature-to-files inventory — the inventory lives in that file). Also state the deployed URL from the ledger (or the blocked-deploy note), every adversarial-audit finding with its CONFIRMED/SUSPECTED label and fixed-or-open status, and the demo-video handoff: the video file path (`<app-name>-video/out/demo.mp4`) plus the narration record (ElevenLabs usage remaining, narration status per line-set, the provider decision-log entries, and the music credit). Take the expansion Phase 6 section from the stage ledger (`.hackathon/run-ledger.md`, expansion section) AND the expansion Phase 6 return text (the landed / blocked / rejected lists). **Named producer:** ORCH-BUILD-MVP composes this section itself, from the stage ledger + the implementers' return texts — mirroring orchestrate, which is the named producer in the orchestrate-driven flow; the return-text half is the implementers' return texts, collected by orch-build-mvp. The report also includes: important design + engineering decisions (what was chosen, what was rejected, and why); the tests and visual checks actually performed (only checks that really ran, with their outcome — never a confident description in place of a check that did not happen); and the highest-value next improvements (prioritized by impact/effort/risk). The report also states the demo video handoff: the video file path (the local filmed video file) AND the instruction "upload this file to YouTube/Vimeo and paste the link into Devpost" — the first build never uploads the video anywhere (it has no YouTube/Devpost account access), so the file path + upload instruction is how the video reaches the submission.

This step covers standalone orch-build-mvp runs only — orchestrate never invokes this skill, so orchestrate never owns this report.

## Example

```
orch-build-mvp: (no argument — reads docs/decision-record.md + docs/scope.md; civicpulse/docs/SDD-v0.6.md is the standalone fallback)
→ read record/scope → slice list (vertical) → scaffold slice 1 (orch-build-mvp step 3)  [GATE 1: auto-approves during a hackathon first build after grill-me, or a one-prompt removal of a first-build feature]
→ /gan-build --skip-planner (generator → evaluator loop) scores vs spec → review (orch-build-mvp step 6)
→ commit feat: (orch-build-mvp step 7)  [GATE 2: auto-approves during a hackathon first build after grill-me, or a one-prompt removal of a first-build feature] → next slice
```
