# orch-build-mvp

Actor · action · target: **orch · build · mvp**. Thin wrapper over the shared
engine in [`orch-pipeline`](../orch-pipeline/SKILL.md).

**Factory routing (fix #29, GLOBAL-ROUTING_F29):** this operation runs through the shared `orch-pipeline` engine, which dispatches all implementation work through the factory — see `orch-pipeline` for the routing (task queue, single-task drones, director briefs, no-guessing, verify-and-merge, cost-aware fan-out). Fan-out is bounded by efficiency: N>3 justified in one line; drones carry minimal context. The orchestrator answers every prompt; drones never answer the user or decide scope (ORCHESTRATOR-ONLY_F29).

**One build engine per run:** this skill is the STANDALONE pipeline — it runs only when the user invokes `/orch-build-mvp` directly. Orchestrate IS the first-build engine; orchestrate never invokes this skill in the same run, and this skill never runs in a first build orchestrate is driving. One engine per run, never both. The GAN harness (orch-build-mvp step 4 below) is the implementer loop WITHIN this standalone pipeline (generator → evaluator per slice), not a separate build engine.

## When to Use

- The user explicitly invoked `/orch-build-mvp` (standalone run) and wants a working vertical slice bootstrapped from the record/scope — `docs/decision-record.md` + `docs/scope.md` by default.
- A doc path in `$ARGUMENTS` (e.g. `civicpulse/docs/SDD-v0.6.md`) is only the standalone fallback when neither record file exists — the record/scope is the default, never the doc path.

## Operation settings

- **Default size floor:** large — this is the full pipeline including Scaffold.
- **Phase mask:** 0 (read the record/scope by default; the spec doc in `$ARGUMENTS` is only the standalone fallback) → 1 → 2 (heavy) → 3 (scaffold) → 4 → 5 → 6. The mask lists the phases that run across the whole skill — NOT the phases step 1 runs: orch-build-mvp step 1 runs orch-pipeline Phases 0–2 only (see the phase mapping in step 1).
- **First move (phase 0 → 2):** read `docs/decision-record.md` + `docs/scope.md` by default — the grill-me decision record and the scope output — and extract scope, locked decisions,
  and the feature list; order it into **thin vertical slices** (one end-to-end
  path first, not all-models-then-all-views). Orch-pipeline Phase 3 (orch-build-mvp step 3) stands up that first slice. If neither record file exists (standalone run, no grill-me), fall back to the doc path in `$ARGUMENTS` or the raw prompt with a stated assumption — never ask the user for a path during a first build.

## How It Works

**Precondition — before the first build auto-approves anything:** check that `docs/decision-record.md` exists (grill-me recorded the decisions) OR the user explicitly chose the skip path ("skip the grilling" / "just build it"). If neither holds, do not auto-approve with zero recorded decisions and no check: proceed on the raw prompt with a stated assumption — do NOT re-run `grill-me` (see hackathon-mode §7).

**Narration-key prompt — once, at the start of the standalone run, never blocking.** At the start of the run (step 1), if the user asked for a demo video and narration will need a key and none is set (no `ELEVENLABS_API_KEY` in the environment, no MiniMax credentials), issue the single `pitch-deck-video` narration-key prompt once. If the user did NOT ask for a demo video, do NOT send this prompt — no video is being built, so no key is needed (ElevenLabs free tier — 10,000 characters a month, no credit card — with the free-tier facts), then continue the build immediately without waiting: the prompt never blocks, the key is an env var only and is never written to any file, and if it never arrives the video renders music-only/silent with a note in the final report. This is the ONE sanctioned user prompt during the standalone run besides grill-me itself (hackathon-mode §7 carve-out) — never a wait point, never an approval gate. Do NOT re-prompt at `/demo` time: the single early prompt covers the run, and a `/demo` dispatched from this run uses the key if present, else falls back to music-only/silent. **Key handoff to a user-invoked `/demo`:** if the user replies with a key mid-run, hold it in working context ONLY and pass it to `/demo` via the dispatch if the user asks for a video: the `/demo` dispatch carries an explicit env instruction naming `ELEVENLABS_API_KEY` with the value held in working context, and the `/demo` executor runs the `tts` step with that variable set in its process environment — the key travels in the dispatch (working context), never in a file; `tts.mjs` reads it only from the environment. If the key arrives after the user-invoked `/demo` already rendered but before the step-9 final report, re-run the video script step (`npm run script` in the video project — tts + render) with the key set, so the delivered video is the narrated cut; if it arrives after the report, note the re-run command in the report with the key redacted (`ELEVENLABS_API_KEY=$KEY npm run script` in the video project dir — the user supplies their own key). **Push boundaries — be trailblazing, not dumb (fix #17 E1).** The design-lead MUST push boundaries and aim to be trailblazing: invent original, first-of-its-kind elements for the page — the unique elements of U1 are the normal case, and a build with no element a template would not produce has not pushed far enough. 'Trailblazing' means original, first-of-its-kind decisions, not safe or derivative ones. 'Not in a dumb way' means EVERY boundary push must still: (1) serve the section's job, named in the Unique-list entry; (2) fit the theme's material world — material, tokens, palette balance, do-nots — **or a recorded departure from it** (D19 reason required) (fix #27, THEME-START_F27); (3) obey the type/space rules — the C3 Type list, the T1 fill rule, measure and contrast checks; (4) be theme-matched (fix #15 rule A); (5) pass the craft floor; (6) pass the Hallmark floor; (7) use no violet; (8) be anti-derivative — never based on a searched reference, and the entry names the theme material it draws on, never a URL; (9) stand or fall on browser-qa's verdict on the rendered screen, which is the final word on whether the invented element reads as distinct rather than generic or template. NOT within reason: a new palette (the Tokens block is the page's `:root` — re-deal once if it clashes); a template pattern (a sections-library recipe reused as-is is a catalogue item, not an invention — it fails U1's not-a-catalogue test); breaking a floor or a ban (craft-floor bans are absolute; the Hallmark floor binds). Inventing a theme direction is a recorded D19 decision, not a forbidden move (fix #27, THEME-START_F27): a departure from the dealt theme is recorded with what was departed from and why the job needs it — a re-deal is the easy path, a recorded departure is the permitted one. Each invented element's Unique-list entry carries the nine-point bound checklist, one line per bound; a missing or failed bound is a static-check finding, and a floor/ban break blocks. Distinctiveness itself is browser-qa's verdict alone.

**Important text uses a unique, important font (fix #20 F5, app surfaces).** On app surfaces, anything supposed to be important uses a unique, important display face, chosen through this skill's type scale and recorded in MASTER.md with its fix #19 D19 reason and its fix #20 F6 justification — never the body face, never a generic/system font. **Fix #20 static checks (all static checks, never screen verdicts).** (F4 scope) The Type list marks the body face as body-only — the body face is the face serving as body/reading text on that build, so a pairing that deals Fraunces as the display face (with a different body face) is checked under F5, not here; no heading, display, hero, call-to-action, or key-label token points at the body face; a dealt theme naming the same face for display and body is either re-dealt with a distinct display face or recorded as a scoped exception with a fix #19 D19 reason and a fix #20 F6 justification. (F5) Every important-text token points at the display face; the display face is recorded with its fix #19 D19 reason and its fix #20 F6 justification; a build setting important text in the body face or a generic/system font is an incomplete build. (F6 record) The decision record states, for the important font on each surface, why it is the impressive choice for that surface; a record that cannot say so is an incomplete build. (F6 verdict) The impressiveness verdict itself is browser-qa's at the finish review, never a static check. (B1) The decision record names the build's brand identity (wordmark, identity tokens, voice); a build with no recorded brand identity is an incomplete build. (X1) Every component entry in the decision record states the experience it creates (what it feels like, what moment it is) alongside the six D19 dimension lines; a component recorded only as a functional block is an incomplete build.

**Fix #21 static checks (all static checks, never screen verdicts).** (F4 tight) The Type list marks the body face as long-body-and-small-text-only — no token for main visible text points at the body face; the body face serves long-length body text and small incidental text only. (F7) Every text element in the Type list — or every genuinely uniform text class — carries its recorded artistic font decision (face + why + job + theme/brand fit); a text element with no recorded decision is an incomplete build; a main visible text element (heading, display, hero, prominent label, price, name, call to action) set in the body face is an incomplete build; a blanket 'all text' class line is not a class decision. (F7 record) The decision record lists the font decision per text element or per uniform class; the D19 reason covers the font choice.

**Fix #23 static checks — type audit (TYPEAUDIT_F23, all static checks, never screen verdicts).** The Type list carries the type-audit table (face | roles | visual share % | element count, per primary screen + build roll-up, visual share = Σ size × visible characters per face ÷ total) and the trio-vs-previous-build line (this build's trio, the previous build's recorded trio, match? + reuse reason if matched; a first build records `previous trio: none (first build)`); a Type list with no type-audit table or no trio line is an incomplete build. (T1 record) The record states the body-face share (≤ 40% roll-up, ≤ 55% per screen), the display-face share (≥ 25% roll-up), and the hero-surface comparison (display > body); a missing share is an incomplete build — the numbers themselves are judged by `browser-qa`, never here. (T2 record) The trio line states whether the trio matches the previous build's; a match with no recorded reuse reason is an incomplete build. (T3 record) The record states the distinct-face count against the variety floor (max(3, ceil(N/20)) for N Type-list text elements, each counted face ≥ 5% share); a count below the floor is an incomplete build. (T1/T2/T3 verdict) Whether a recorded share, trio, or count FAILS the build is `browser-qa`'s verdict on the rendered screen alone — this check records the numbers, never the verdict. **Adversarial audit (a distinct named step, inside step 6, after the `code-reviewer` pass):** `code-reviewer` (+ `security-reviewer` on any security-trigger slice) audits the built code as a skeptical staff engineer — try to break it, falsify the claimed behaviour. Every finding carries a severity (blocker / major / minor) and is marked **confirmed** (reproduced against the running code) or **suspected** (reasoned but not reproduced) — a suspected finding is never presented as a confirmed defect. Fix blockers and majors inside the capped 2-round fix loop; minors go in the final report.

when the tree has no repo, verify against the snapshot manifest in `docs/run-ledger-appendix.md` (the `<redesign-id>` section) alone — each restored path diffed against its snapshot copy and its recorded hash — the manifest check is the fallback and the authority, `git status` is only a convenience. A file that cannot be restored from the snapshot is named in the ledger and final report as a snapshot-coverage gap (the hold stands regardless); (3) record `re-verification <redesign-id>: BLOCKED` + snapshot path + reverted files in the ledger and final report (the ledger's `fresh-verdict rounds used: N/2` line is untouched by the revert — run state is never restored — so the round spent on the failed re-verification stays spent); (4) keep the deploy/commit hold — the redesign is not deployed, not committed, not filmed, and not reported as landed.
