# orch-change-feature

Actor · action · target: **orch · change · feature**. Thin wrapper over the
shared engine in [`orch-pipeline`](../orch-pipeline/SKILL.md).

## When to Use

- An existing feature **works**, but the desired behavior is different ("change",
  "adjust", "make it also …", "instead of X do Y").
- Distinguish from siblings:
  - **not** broken → not `orch-fix-defect` (no bug to reproduce).
  - **not** new → not `orch-add-feature` (the capability already exists).

## Operation settings

- **Default size floor:** small — most tweaks are a function or two.
- **Phase mask:** 0 → (1 only if the new behavior needs research) → light 2 →
  4 → 5 → 6.
- **First move (phase 4):** update the *existing* tests to express the new
  desired behavior, then change the implementation until they pass. Changing the
  tests first is what separates a tweak from a fix.

## How It Works

1. Run the `orch-pipeline` engine with the settings above.
2. Keep the plan light — only `standard`+ size warrants the full planning pass.
3. Stop at **Gate 1** (plan / changed-test approval) and **Gate 2** (pre-commit) — except during a hackathon first build after grill-me, or a one-prompt removal of a first-build feature, where both gates auto-approve and the run proceeds without waiting (see hackathon-mode §7).
4. Add `security-reviewer` if the change touches a security trigger.

## Landing redesigns

When the change is a redesign of the landing/company page — a new visual direction that keeps every fact, link, form, field, handler, route, id, and test hook — route the design work through the Hallmark redesign flow: `skills/design-taste-frontend/SKILL.md` (redesign paragraph before step 5) and the procedure in `references/hallmark/references/redesign.md`. Record the before-state first (`sloplint --before`, links/fields/handlers/headings + screenshots to `.hallmark/before*`), build, then `sloplint --kept` — anything lost is `FAIL kept` / `WARN kept`. Depths: **full** (system + composition change; default), **restyle** (system only, keep the layout), **polish** (only what a gate names). A dashboard/app-surface change is not a landing redesign — route that to `ui-ux-pro-max` instead. After rebuilding a redesigned landing page, re-run the Hallmark hero review and update `.hallmark/hero-review.md` with the new findings and settlements before finishing — the old file holds pre-redesign findings, which Verify would otherwise read as current. The engine steps above still run (tests first, gates auto-approve during a hackathon first build after grill-me or a one-prompt removal); the redesign flow owns only the design work.

## Removing a feature

When the request is to remove a feature — including a one-prompt removal of a first-build feature routed here by orchestrate:

1. Find the feature's files from the final report's feature-to-files inventory, or, if there is no inventory, trace the feature with `code-explorer` first and list its files before deleting anything.
2. Delete its tests, implementation code, routes, and UI, and drop any database objects it alone owns (tables, columns). Never delete an already-applied migration file — that is drift: write a new down-migration that drops what the feature alone owned instead. Apply the change to the remote database as well as locally (e.g. `supabase db push` per `deploy-fast`) — a local-only migration never reaches the deployed app. Also drop or recompute shared/derived database objects that depended on the removed feature — for example a `vote_count` column on `dishes` derived from the removed feature's data: drop the column if nothing else uses it, or recompute it from the remaining data. For a shared table holding rows from several features (neither owned alone nor derived), drop only the removed feature's columns and rows — never the shared table.
3. Verify nothing still references the removed code, routes, UI, or database objects — grep the repo for the feature's identifiers (component, function, route, and table/column names) and check every file in the final-report inventory's entry for the feature — and fix or remove any dangling references, with a CAP of 2 passes: one fix per found reference, then re-grep once; if new references keep appearing after 2 passes, mark the removal blocked in the final report (with the still-dangling references as evidence) and skip to step 6 and deliver the updated final report — never loop unboundedly on dangling references.
4. Run the tests and the app to confirm the removal did not break anything else, then commit under the usual gates (auto-approved during a hackathon first build after grill-me, or a one-prompt removal of a first-build feature). If the tests fail or the app breaks after the deletion, fix with a CAP of 2 fix rounds: after 2 rounds, if it is still broken, do NOT commit it broken and do NOT loop unboundedly — mark the removal blocked in the final report (with the failing test or the broken behaviour as evidence), stop, and leave the deletion uncommitted — then skip to step 6 and deliver the updated final report. A failing TEST suite follows a DIFFERENT rule from the orch-pipeline review-findings rule (an unresolvable CRITICAL review finding is recorded as blocked and the commit proceeds under auto-approval): a review finding is about the diff's quality, but a failing test suite means the app itself is broken, so the commit does NOT proceed — the removal is blocked instead.
5. After the commit, re-deploy: if the project has a git remote linked to the deploy, push the removal commit to `main` — the git-linked deploy fires from that push (`deploy-fast`); otherwise redeploy via the path `deploy-fast` established in the first build (Vercel CLI link / `railway up` / `supabase db push`). Do not assume a git remote exists — no first-build step creates a GitHub repo, sets a git remote, or links Vercel to git (deploy-fast's Vercel CLI deploy links the local folder, not git). If neither a git-linked deploy nor a deploy-fast path exists, the blocked-deploy handling below applies. A push redeploys ONLY the Vercel frontend: a split backend does NOT redeploy from it — redeploy the Railway API/backend separately with `railway up` from the backend directory, and apply any migration with `supabase db push` (both per `deploy-fast`, split-backend redeploy). Do not run an interactive deploy CLI for this step (per `deploy-fast` — never stall on a login): if a deploy CLI is unauthenticated (or the project has no git-linked deploy), do not wait for a login — the removal still counts as done-with-blocked-deploy; note the blocked deploy in the final report and move on. That covers the Vercel/Railway deploy CLIs AND `supabase db push`: an unauthenticated Supabase CLI is blocked-deploy handling too — record it as blocked in the final report with the exact command and error, never stall on an interactive `supabase login`. After the redeploy, wait for the deploy to be ready before re-filming — UNLESS the deploy was already known-blocked (blocked-deploy handling above: no git-linked deploy, no deploy-fast path, or an unauthenticated deploy CLI): in that case skip the poll entirely, film local immediately, and note it in the final report — polling a URL that can never become ready burns up to ~5 minutes for nothing. Otherwise take the deployed URL and deploy path from `.hackathon/run-ledger.md` (or `docs/final-report.md` if the ledger is absent), then poll the deployed app until it serves the new version (no removed feature, no dangling references), with a BOUNDED wait — check every ~30s, stop after ~5 minutes. If it never becomes ready in that bound, film local and note it in the final report — never film a stale deployed URL, and never wait unboundedly. Then, before re-filming, update `shots.json` FIRST relative to the re-film — remove the feature's shots, selectors, and narration lines (FIRST means first before the re-film, not first in this step overall: the push/re-deploy above precedes it) — then re-check every remaining shot against the updated demo storyboard in `docs/scope.md` (move the feature to the cut list first, so the storyboard is current): a shot whose feature was removed, or whose narration still promises the removed feature, is removed or rewritten before the re-film — then re-film via `/demo --rebuild`, which films the LOCAL app from the project dir (`APP_DIR`/project root), never a deployed URL; if the deploy was blocked, film local anyway and note in the final report that the video shows the local app, not the deployed one. **Narration continuity on the re-film:** narration lines that did not change are served from the per-line cache — the cached wavs from the first build are reused in their ORIGINAL voice (the cache key is the configured provider, and `reconcileNarration` restores a line whose wav is on disk), so a keyless removal run does NOT re-synthesise them in a fallback voice and does NOT go silent. If any narration line CHANGED (not just deleted) and no `ELEVENLABS_API_KEY` is set, issue the single `pitch-deck-video` narration-key prompt once (same prompt as the first build — free tier, 10,000 chars/month, no credit card), then continue without waiting: the key is an env var only, never written to a file. If the key never arrives, the changed lines render per the `tts.mjs` fallback and the step-6 report MUST state the narration status per line-set (unchanged lines: original voice reused; changed lines: voice actually rendered) — never present the video as fully narrated in the original voice when it is not. After re-filming, IF a hosted video link exists (in the Devpost submission, the README, or the final report), re-upload the new video to the same YouTube/Vimeo host (upload HOURS before the deadline — processing can take several hours, per `devpost-autofiller`) and update the video LINK wherever it appears (the Devpost submission and the README if it embeds it) — text updates alone leave the judge-visible artefact stale, so the link must point at the re-uploaded video, not the pre-removal one; ELSE (no hosted video link exists — the first build never uploads the video anywhere, so there is nothing to re-upload to) record in the final report "video re-filmed locally at <path>, not yet hosted — upload it and update the link at <location>" and deliver that report. Never claim a re-upload happened when it did not. The removal's done-condition ("the demo video reflects the removal") is satisfied by the re-filmed LOCAL video + the honest hosting note, not by a phantom upload. Then update the stage ledger (`.hackathon/run-ledger.md`), `docs/scope.md` (move the feature from the must-have list to the cut list and update the demo storyboard), the README (`readme-writer`), the pitch narrative, scripts, and demo storyboard (`hackathon-pitch` — refresh them only where those artifacts already exist, so the pitch no longer promises the removed feature; if no pitch artifacts exist yet, say so in the final report rather than leaving it silently stale), and the Devpost submission (`devpost-autofiller`) if one exists — if no Devpost submission exists yet there is nothing to update, say so in the final report rather than leaving it silently stale — and the feature-to-files inventory in `docs/final-report.md` — remove the feature's entry, or mark it Removed and keep its file list, so a later reader can see what was removed and where it lived — a removal is not done until the deployed app, the demo video, the ledger, and the inventory all reflect it; none of them may go stale.
6. Deliver the updated final report as the reply — this is the done signal for the removal. Update `docs/final-report.md` first (feature-to-files inventory plus what was removed, anything blocked, the re-uploaded video link if a hosted video existed, else the honest hosting note from step 5 — "video re-filmed locally at <path>, not yet hosted" — AND the narration status of the re-filmed video: full / partial / none, and which voice rendered the narration — original ElevenLabs voice reused for unchanged lines, or the fallback voice for changed lines when no key arrived), then deliver the updated report as the reply. The first-build-only delivery rule in hackathon-mode §7 / orchestrate covers the first build's final report, NOT removals — this step is what covers removals, so a removal is not done until this delivery has happened.

 `/demo` vs `/demo --rebuild`: plain `/demo` scaffolds a fresh video project (it copies the template into a new `<app-name>-video/` directory) — the pitch-deck-video skill does not define what plain `/demo` does when that directory already exists, so never run it over an existing video project, and never copy the template's seed `shots.json` over the edited one; on an existing project always re-film with `/demo --rebuild`, which re-records and re-cuts the existing project from its current `shots.json`.

A removal is not done until the reference check in step 3 is clean.

## Example

```
orch-change-feature: make nws-poller alert at 2 warnings instead of 3
→ update threshold tests to new spec → change impl to green
→ code-review → commit  [GATE 2: auto-approves during a hackathon first build after grill-me, or a one-prompt removal of a first-build feature]
```
